# Piece 5: Sound Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the DMG audio processing unit so that the twelve blargg
sound ROMs and `boot_hwio` pass — 126/165 to 139/165.

**Architecture:** `src/core/apu/`, one file per channel plus shared
length/envelope/sweep components, behind an `Apu` that owns the registers,
the power state and the mixer. The 512 Hz frame sequencer is clocked from a
falling edge of bit 12 of the system counter, not from a free-running timer.

**Tech Stack:** C++20, MSVC (Visual Studio 2026), CMake + Ninja, doctest.
Windows only. `cmake` and `cl` are not on PATH — every build command goes
through `tools\dev.cmd`.

**Spec:** `docs/superpowers/specs/2026-09-23-sound-design.md`. Read it before
Task 1.

## A note on this plan's form

Exact masks, exact step orders and exact test cases; **no large blocks of
finished implementation code**. In piece 3 the code written into the plan
from memory was wrong in five of eleven tasks and each wrong block cost a
correction round; pieces 3b and 4 carried values without invented code and
needed none.

Where this plan gives a number or a mask, use it. Where it describes
behaviour, write the code from Pan Docs' "Audio Registers" and "Audio
Details" pages and the spec. **Where this plan says a value is from memory
of Pan Docs, check the document — the document governs, not this plan.**

### Task 1: One place that knows about system-counter edges

No score moves. This is piece 2's outstanding must-do, and it must land
before the frame sequencer is written, because the sequencer is the second
consumer.

**Files:**
- Modify: `src/core/Timer.h`, `src/core/Timer.cpp`, `src/core/Serial.h`, `src/core/Serial.cpp`, `src/core/GameBoy.cpp`
- Test: `tests/test_timer.cpp`, `tests/test_serial.cpp`

**The problem.** The 16-bit system counter lives in `Timer`. `Serial` reads
it through `Timer::counter()` and works out bit 8's falling edge itself, and
`GameBoy` resets it on STOP by calling `setCounter(0)`. The APU would be a
third consumer of the same counter with its own edge arithmetic.

**What to build.** `Timer` becomes the one thing that knows when a counter
bit falls. Give it a query that answers, for a given bit, whether this
M-cycle produced a falling edge of that bit — and have `Timer::tick()`
compute the before/after pair once. Move `Serial` onto it; leave serial's
behaviour identical. Keep `counter()` and `setCounter()` — SST and the boot
tests use them — but nothing outside `Timer` should compute an edge again.

**Interfaces — produces:** an edge query on `Timer` that `Serial` uses in
this task and the APU uses in Task 3. Name it for what it answers. Whatever
signature you choose, state it in your report, because Task 3's implementer
will be given it.

**Power (NR52 bit 7).**
- Writing bit 7 = 0 zeroes every register FF10-FF25 and makes further
  writes to them do nothing. **Wave RAM is not cleared and stays
  accessible.** NR52's own low bits read the channel-enabled flags, which
  all become 0.
- On DMG only, the length bits of NR11, NR21, NR31 and NR41 **remain
  writable while powered off**. That is the whole of
  `08-len_ctr_during_power`, and it is a DMG/CGB difference — do not take a
  CGB-flavoured reading of Pan Docs here.
- Writing bit 7 = 1 powers on and resets the frame sequencer's step counter.
- NR52 bits 0-3 are read-only channel-enabled flags, one per channel.

**The power-on register values** are Pan Docs' "Power Up Sequence" table.
From memory of that table the *read* values on DMG are NR10 0x80, NR11 0xBF,
NR12 0xF3, NR13 0xFF, NR14 0xBF, NR21 0x3F, NR22 0x00, NR23 0xFF, NR24 0xBF,
NR30 0x7F, NR31 0xFF, NR32 0x9F, NR33 0xFF, NR34 0xBF, NR41 0xFF, NR42 0x00,
NR43 0x00, NR44 0xBF, NR50 0x77, NR51 0xF3, NR52 0xF1. **Check every one of
these against Pan Docs before using them — this plan is quoting from memory
and the document governs.** `boot_hwio` is the arbiter that will tell you if
both are wrong.

Wave RAM's power-on contents differ between DMG units and are not fixed; if
`boot_hwio` checks FF30-FF3F, follow what it requires and record the choice.

### Task 3: The frame sequencer and the length counter

**Files:**
- Create: `src/core/apu/LengthCounter.h`, `tests/test_length_counter.cpp`
- Modify: `src/core/apu/Apu.h`, `src/core/apu/Apu.cpp`, `tests/test_apu.cpp`

**Consumes:** the system-counter edge query from Task 1 — your dispatch will
carry its exact signature.

**The sequencer.** Eight steps, advanced on each **falling edge of bit 12 of
the system counter**. Step order, from step 0:

| step | clocks |
| --- | --- |
| 0 | length |
| 1 | — |
| 2 | length, sweep |
| 3 | — |
| 4 | length |
| 5 | — |
| 6 | length, sweep |
| 7 | envelope |

Lengths at 256 Hz, sweep at 128 Hz, envelope at 64 Hz — those rates are the
consequence of this table, not separate timers. Do not build three timers.

**The length counter**, shared by all four channels:
- Channels 1, 2 and 4 count 64 down to 0; channel 3 counts 256 down to 0.
  A write to NRx1 sets the counter to (maximum − the value written).
- It is clocked only when enabled by bit 6 of NRx4, and only on a length
  step. Reaching 0 disables the channel.
- **The extra-clocking quirk:** enabling length (writing bit 6 of NRx4 from
  0 to 1) during the *first half* of a sequencer period — that is, when the
  next step will not clock length — clocks the counter once immediately. If
  that takes it to 0, the channel is disabled.
- **On trigger:** if the length counter is 0 it reloads to maximum. If
  length is enabled and the trigger happens in that same first half, the
  reloaded counter is immediately clocked once.

This is `02-len_ctr` and `07-len_sweep_period_sync`, and it is the fiddliest
part of the piece. Read Pan Docs' "Audio Details — Length Counter" in full
before writing it.

- [ ] **Step 1: Write `tests/test_length_counter.cpp`, and run it to watch it fail.** Test `LengthCounter` directly, not through a channel.
  - a counter loaded with 1 and clocked once disables its channel
  - a counter loaded with 0 is treated as maximum on trigger
  - clocking does nothing while length is disabled
  - the extra clock on enabling in the first half of the period, and **no**
    extra clock when enabling in the second half
  - a trigger with a zero counter reloads to maximum, and to maximum − 1
    when the extra clock applies
  - channel 3's maximum is 256, not 64
- [ ] **Step 2: Add sequencer cases to `tests/test_apu.cpp`:** the step advances on a falling edge of counter bit 12 and not otherwise; a DIV write that produces that edge steps it; powering on resets the step to 0.
- [ ] **Step 3: Implement.**
- [ ] **Step 4: Build, run the unit suite.** Expected: all pass.
- [ ] **Step 5: Mutation-test.** Apply each, rebuild, confirm a red, revert: clock length on every step instead of the four; drop the extra-clock quirk; apply the extra clock in both halves; use 64 as channel 3's maximum.
- [ ] **Step 6: Run `--only dmg_sound`.** `02-len_ctr` and `08-len_ctr_during_power` are the targets. Report what moved.
- [ ] **Step 7: Full run, scoreboard, commit, push** if anything moved; commit without the scoreboard if nothing did.

### Task 4: The pulse channels

**Files:**
- Create: `src/core/apu/PulseChannel.h`, `src/core/apu/PulseChannel.cpp`, `src/core/apu/VolumeEnvelope.h`, `tests/test_pulse_channel.cpp`
- Modify: `src/core/apu/Apu.h`, `src/core/apu/Apu.cpp`, `CMakeLists.txt`

**Duty cycles — use verbatim.** NRx1 bits 6-7 select one of four 8-step
patterns:

| duty | pattern |
| --- | --- |
| 0 | 0,0,0,0,0,0,0,1 (12.5%) |
| 1 | 1,0,0,0,0,0,0,1 (25%) |
| 2 | 1,0,0,0,0,1,1,1 (50%) |
| 3 | 0,1,1,1,1,1,1,0 (75%) |

**The frequency timer** counts up from (2048 − frequency) × 4 T-cycles; on
expiry it reloads and advances the duty position by one, wrapping 7 → 0. The
11-bit frequency is NRx3 plus the low 3 bits of NRx4.

**The envelope** (NRx2): bits 7-4 initial volume, bit 3 direction (1 up),
bits 2-0 period. A period of 0 means the envelope does not step at all. On
an envelope step the volume moves by one toward 0 or 15 and stops at the
end; it does not wrap.

**The DAC** is off when the top 5 bits of NRx2 are all 0 — that is, volume 0
and direction down. Turning the DAC off **disables the channel**; turning it
on does not enable it.

**Trigger** (bit 7 of NRx4): enable the channel unless its DAC is off;
reload length if 0; reload the frequency timer; reload the envelope's timer
and volume from NRx2.

- [ ] **Step 1: Write `tests/test_pulse_channel.cpp`, and run it to watch it fail.**

    the position advances every 4 T-cycles, at 0 every 8192
  - the envelope steps by one per envelope clock, stops at 0 and at 15, and

  - writing 0x00 to NRx2 disables the channel; writing a non-zero top 5 bits
    does not re-enable it without a trigger
  - trigger enables the channel, reloads the frequency timer and reloads the

  - trigger with the DAC off leaves the channel disabled
- [ ] **Step 2: Implement `PulseChannel` and `VolumeEnvelope`,** and wire channels 1 and 2 into `Apu` — channel 2 is the same channel without a sweep, so build one type and give channel 1 the sweep in Task 5.

### Task 5: The sweep

**Files:**
- Create: `src/core/apu/FrequencySweep.h`, `src/core/apu/FrequencySweep.cpp`, `tests/test_sweep.cpp`
- Modify: `src/core/apu/PulseChannel.h`, `src/core/apu/PulseChannel.cpp`, `CMakeLists.txt`

Four of the twelve ROMs are about this one component: `04-sweep`,
`05-sweep_details`, `06-overflow_on_trigger`, `07-len_sweep_period_sync`.

**NR10:** bits 6-4 period, bit 3 direction (1 = decreasing), bits 2-0 shift.

**The shadow register.** On trigger: copy the channel's frequency into the
shadow register, reload the sweep timer with the period (**a period of 0 is
treated as 8**), set the enabled flag if either period or shift is non-zero,
and **if shift is non-zero, run the overflow check immediately** — which can
disable the channel before a single sweep step has happened. That immediate
check is `06-overflow_on_trigger`.

**A sweep step:** compute the new frequency from the shadow register, shifted
right by the shift amount, added or subtracted. If it exceeds 2047 the
channel is disabled. Otherwise, **if the shift is non-zero**, write it back
to both the shadow register and NR13/NR14, then run the overflow check a
second time on a further calculation — the second check does not write back.

**The negate latch:** once a calculation has been done in decreasing mode,
clearing the direction bit in NR10 disables the channel. This is the detail
`05-sweep_details` exists for.

- [ ] **Step 1: Write `tests/test_sweep.cpp`, and run it to watch it fail.** Test `FrequencySweep` directly.
  - a period of 0 in NR10 makes the timer reload with 8
  - trigger with a non-zero shift runs the overflow check at once and
    disables the channel when the result exceeds 2047
  - trigger with shift 0 does **not** run that check
  - a step writes the new frequency back to the shadow register and to the
    channel, and only when the shift is non-zero
  - the second overflow check after a step does not write back
  - the negate latch: after a decreasing calculation, clearing the direction
    bit disables the channel; without such a calculation it does not
- [ ] **Step 2: Implement, and give channel 1 its sweep.**
- [ ] **Step 3: Build, run the unit suite.** Expected: all pass.
- [ ] **Step 4: Mutation-test.** Apply each, rebuild, confirm a red, revert: treat a period of 0 as 0; skip the overflow check on trigger; write back on the second check too; drop the negate latch.
- [ ] **Step 5: Run `--only dmg_sound`.** Four ROMs are in scope.
- [ ] **Step 6: Full run, scoreboard, commit, push.**

### Task 6: The wave channel

**Files:**
- Create: `src/core/apu/WaveChannel.h`, `src/core/apu/WaveChannel.cpp`, `tests/test_wave_channel.cpp`
- Modify: `src/core/apu/Apu.h`, `src/core/apu/Apu.cpp`, `CMakeLists.txt`

Three ROMs, all about the same DMG quirk: `09-wave_read_while_on`,
`10-wave_trigger_while_on`, `12-wave_write_while_on`.

**The channel.** 32 four-bit samples packed into the 16 bytes at FF30-FF3F,
high nibble first. The frequency timer period is (2048 − frequency) × 2 —
**half** the pulse channels' period, which is why the same frequency value
sounds an octave higher. NR32 bits 6-5 select the output level: 0 mute, 1
full, 2 half, 3 quarter, applied as a right shift of 4, 0, 1, 2. The DAC is
controlled by bit 7 of NR30, not by an envelope — this channel has none.

**The DMG quirk, which is the whole point of the three ROMs.** While the
channel is enabled, the CPU cannot see wave RAM freely:
- a read of FF30-FF3F returns the byte the channel is currently reading, and
  0xFF unless the access falls within a few T-cycles of the channel's own
  read;
- a write lands on that same byte, and is dropped otherwise;
- triggering the channel while it is already playing corrupts the first
  bytes of wave RAM.

Pan Docs describes these under "Audio Details — Wave RAM". The exact timing
window and the exact corruption pattern are what the ROMs measure. Implement
Pan Docs, run the ROMs, and where a ROM disagrees follow the ROM and write
the `docs/known-divergences.md` entry with the evidence.

- [ ] **Step 1: Write `tests/test_wave_channel.cpp`, and run it to watch it fail.**
  - the 32 samples are read high nibble first, in order, wrapping after 31
  - the frequency timer period is (2048 − frequency) × 2
  - the four output levels shift by 4, 0, 1 and 2
  - clearing bit 7 of NR30 disables the channel
  - with the channel off, wave RAM reads and writes are ordinary
  - with the channel on, a read outside the access window returns 0xFF and a
    write outside it is dropped
  - the sample position on trigger — assert whatever Pan Docs states, and
    record it if a ROM later disagrees
- [ ] **Step 2: Implement.**
- [ ] **Step 3: Build, run the unit suite.** Expected: all pass.
- [ ] **Step 4: Mutation-test.** Apply each, rebuild, confirm a red, revert: use (2048 − f) × 4 as the period; read the low nibble first; make wave RAM freely accessible while on; apply level 3 as a shift of 3.
- [ ] **Step 5: Run `--only dmg_sound`.** Three ROMs are in scope.
- [ ] **Step 6: Full run, scoreboard, commit, push.**

### Task 7: The noise channel, and the mixer

**Files:**
- Create: `src/core/apu/NoiseChannel.h`, `src/core/apu/NoiseChannel.cpp`, `tests/test_noise_channel.cpp`
- Modify: `src/core/apu/Apu.h`, `src/core/apu/Apu.cpp`, `tests/test_apu.cpp`, `CMakeLists.txt`

**The LFSR.** 15 bits, all 1 on trigger. A step XORs bits 0 and 1, shifts
right, and puts the result in bit 14; when NR43 bit 3 (width) is set it also
puts it in bit 6, making the sequence much shorter. The channel's output is
the **inverted** bit 0.

**The frequency timer.** NR43 bits 2-0 are a divisor code: code 0 means a
divisor of 8, codes 1-7 mean the code × 16. The period is that divisor
shifted left by NR43 bits 7-4. Shift values 14 and 15 are invalid and stop
the channel.

**The mixer.** Each channel produces a digital level 0-15. NR51 routes each
channel to left, right, both or neither — bits 0-3 are the four channels on
the right, bits 4-7 the same four on the left. NR50 bits 6-4 are the left
master volume and bits 2-0 the right, each scaling by (volume + 1) / 8.
NR50's bit 7 and bit 3 are the Vin mixers: no cartridge in the test set
drives Vin, so they contribute nothing — say so in a comment rather than
silently ignoring them.
