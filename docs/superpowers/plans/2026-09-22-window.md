# Piece 3b: a window you can play in. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Load a Game Boy ROM in a window, see it run at the real frame rate, and play it with the keyboard.

**Architecture:** A new `app/` executable links `fourshades_core` and owns everything the core must not know about: SDL3, a window, a texture, a palette, a keyboard, and a save file. The core gains only what it genuinely lacks — real joypad state, and accessors for cartridge RAM — never a dependency on the app.

**Tech Stack:** C++20, MSVC, CMake + Ninja through `tools\dev.cmd`, SDL3 pinned and vendored, doctest.

**Spec:** `docs/superpowers/specs/2026-09-22-window-design.md`

## A warning from the previous piece

The piece-3 plan contained code written from memory, and **five of its eleven sections were wrong** — a hook placed in a function that never runs for the case it targeted, a constant that left a test measuring nothing, a helper that no longer compiled. Each cost a task's worth of rework.

So this plan deliberately does **not** paste large code blocks. It states precisely what must be true, with exact values and exact interfaces, and every task begins by reading the real headers. If this plan and the code disagree, **the code is right** — report the discrepancy rather than following the plan off a cliff.

## Global Constraints

- Everything from pieces 1-3 still holds: Windows only; C++20; build through `.\tools\dev.cmd` from PowerShell in `C:\GameMode`; stage explicit paths, never `git add -A`; `Co-Authored-By:` naming the model that wrote the commit; no double-quote characters in commit messages (this environment's PowerShell mangles them — use `git commit -F -` with a heredoc).
- **The scores must not move.** SingleStepTests stays `499 / 500` (only opcode `10`, on `pc`); test ROMs stay `106 / 165` with `ppu timing` 12/12, `oam bug` 7/7, `screen` 4/30. This piece adds a way to *look at* the emulator. The only exceptions are the joypad register and STOP's wake-up, which are core behaviours with hardware documents behind them — and if either moves a ROM's verdict, that is a finding to report, not a result to accept.
- `python tools/check_core_isolation.py` must keep passing. `src/core` must never learn that SDL, a window, a file, or a save exists.
- Never loosen a detector, the runner, a comparator, or a time limit.
- Third-party code is pinned and hash-verified, never committed. Follow the pattern in `tools/sst/fetch_sst.py` and `tools/roms/fetch_roms.py`.
- The divergence rule: Pan Docs outranks an emulator-generated test; a hardware-verified test outranks a Pan Docs sentence that proves to be a simplification. Record decisions in `docs/known-divergences.md` with their evidence.

## What the core already gives you

Read these for yourself before writing anything; they are quoted here only so you know they exist.

- `GameBoy(Cartridge)`, `step()`, `cycles()` (M-cycles), `ppu()`, `peek()`, `read()`, `write()`.
- `Cartridge::load(std::vector<u8> rom, std::string* error) -> std::optional<Cartridge>`.
- `Ppu::frame()` — `const std::array<u8, 160*144>&` of shade indices 0-3 — plus `frameCount()`, `kWidth`, `kHeight`.
- The joypad seam: `GameBoy`'s I/O read of `0xFF00` currently returns `0xC0 | joypadSelect_ | 0x0F`, with a comment saying no buttons are held. That is the line Task 3 makes real.

### Task 1: Vendor SDL3

Nothing visible yet. This task makes SDL3 available to the build the way every other dependency here is: pinned, hash-verified, downloaded on demand, never committed.

**Files:** create `third_party/sdl/fetch_sdl.py`, `third_party/sdl/manifest.sha256`, `third_party/sdl/README.md`; modify `.gitignore`, `CMakeLists.txt`.

- [ ] **Step 1: Read how the existing fetchers work.** `tools/sst/fetch_sst.py` and `tools/roms/fetch_roms.py` both download, verify against a committed manifest of SHA-256 hashes, and refuse to proceed on a mismatch. Follow that shape — including the per-file retry behaviour, which exists because a large download failed repeatedly early in this project.
- [ ] **Step 2: Pin a release.** Use the SDL3 Windows VC development archive from the official SDL releases. Record the exact version and the archive's SHA-256 in `manifest.sha256`. The script downloads, verifies, and extracts into `third_party/sdl/SDL3-<version>/`. On a hash mismatch it must fail loudly and delete nothing.
- [ ] **Step 3: Ignore the extracted tree** in `.gitignore`, the same way `tools/sst/data/` and `tools/roms/data/` are ignored. Commit the script and the manifest only.
- [ ] **Step 4: Wire CMake.** The root `CMakeLists.txt` finds the extracted SDL3 and exposes it as an imported target. If SDL3 is absent, configuring must fail with a message naming the fetch script — never a silent skip that produces a build with no window.
- [ ] **Step 5: Prove it links.** A trivial target that calls `SDL_GetVersion()` and prints it. Build it, run it, quote the output.
- [ ] **Step 6: Verify nothing else moved.** Build, `.\build\release\fourshades_tests.exe`, both runners, `python tools/check_core_isolation.py`. Scores unchanged.
- [ ] **Step 7: Commit.** Explicit paths.

### Task 2: A window with a picture in it

**This is the task where the screen appears.** By the end of it you can run a ROM and watch it draw, with no input yet.

**Files:** create `app/CMakeLists.txt`, `app/main.cpp`, `app/Screen.h`, `app/Screen.cpp`; modify `CMakeLists.txt`; test `tests/test_screen.cpp`.

- [ ] **Step 1: Write the failing test.** `Screen`'s two pure functions are testable without a window, and those are what gets tested:
  - `shadeToRgb(Palette, u8 shade) -> u32`. Grey is white `0xFFFFFF`, light `0xAAAAAA`, dark `0x555555`, black `0x000000` for shades 0-3 — the same four values the reference images the scoreboard compares against contain. Green is the classic DMG `0x9BBC0F`, `0x8BAC0F`, `0x306230`, `0x0F380F`. Assert every shade of both palettes, and assert a shade above 3 is rejected rather than masked — this project has been bitten by silent masking before.
  - `fitRect(windowW, windowH) -> {scale, x, y, w, h}`. Integer scaling only: the largest whole multiple of 160x144 that fits, centred. Assert 640x576 gives scale 4 exactly; 700x600 gives scale 4 centred with a border, not 4.37; and a window smaller than 160x144 gives scale 1 rather than 0.
- [ ] **Step 2: Run it and watch it fail.**
- [ ] **Step 3: Implement `Screen`.** One streaming texture 160x144, nearest-neighbour, drawn into the rect `fitRect` returns, with the rest of the window filled by a neutral border.
- [ ] **Step 4: Implement `main.cpp`.** Takes a ROM path. With no argument, print what was expected and exit non-zero — do not open an empty window. Read the file, `Cartridge::load`, report its error text verbatim on failure, construct a `GameBoy`.
- [ ] **Step 5: The frame loop.** Step the machine until `ppu().frameCount()` increases, then present `ppu().frame()`. Drive the loop from the frame counter rather than a cycle count, so it stays correct if timing is ever refined. Pace to **59.727 Hz** — the DMG's real rate, not the monitor's 60 — and say in a comment why that matters (piece 5's audio would inherit any drift). Closing the window exits cleanly.
- [ ] **Step 6: Run a ROM and look at it.** Use one of the test ROMs already on disk under `tools/roms/data/`. `acid/dmg-acid2.gb` is a good choice: the emulator passes it, so you know what it should look like. Say in your report what you saw.
- [ ] **Step 7: Verify nothing else moved,** as Task 1 Step 6.
- [ ] **Step 8: Commit and push.**

### Task 3: Buttons

The joypad register has existed since piece 2 and has always answered "no buttons held". This task gives it real state, its interrupt, and the wake-up that STOP has been waiting on since piece 1.

**Files:** create `src/core/Joypad.h`, `src/core/Joypad.cpp`, `app/Input.h`, `app/Input.cpp`; modify `src/core/GameBoy.*`, `src/core/Cpu.cpp`, `app/main.cpp`, `CMakeLists.txt`; test `tests/test_joypad.cpp`.

- [ ] **Step 1: Read Pan Docs on the joypad** (`https://gbdev.io/pandocs/Joypad_Input.html`) and the current `0xFF00` handling in `GameBoy`. Note that the register is **active low** — a pressed button reads 0 — and that both select bits can be clear at once, in which case the low nibble is the AND of both groups.
- [ ] **Step 2: Write the failing tests.** For every combination of the two select bits: buttons pressed in, correct low nibble out, bits 7-6 always set. Assert the interrupt fires on a **high-to-low transition** of any selected line, and does not fire on a press that is not selected. Assert a press with neither group selected still reads correctly. Each assertion must fail if the behaviour it names is wrong — break the behaviour and watch it, the way Task 10 of the previous piece did.
- [ ] **Step 3: Implement `Joypad`** as a small class the core owns: a button mask in, a register value out, and the IF bit when a line falls.
- [ ] **Step 4: STOP's wake-up.** Pan Docs' exit from STOP is a button press, which was impossible while no button could be pressed. Implement it, test it, and update the STOP entry in `docs/known-divergences.md` — which currently says joypad input arrives with this piece, so it is the entry that gets closed.
- [ ] **Step 5: Map keys in the app.** Arrows for the pad, Z and X for A and B, Enter and Backspace for Start and Select. Read once per frame, hand the core a mask. Key mapping lives in `app/`, never in the core.
- [ ] **Step 6: Verify.** Both runners must be unchanged — **if a ROM's verdict moves, stop and report it**, because a real joypad is exactly the kind of change that could legitimately alter one, and that deserves an explanation rather than a shrug.
- [ ] **Step 7: Commit and push.**

### Task 4: Saves that survive being interrupted

A cartridge with a battery expects its RAM to persist. This is the first thing this project writes that a person would be upset to lose, so the failure mode is the point of the task.

**Files:** create `app/Save.h`, `app/Save.cpp`; modify `src/core/Cartridge.*`, `app/main.cpp`; test `tests/test_save.cpp`.

- [ ] **Step 1: Give the core the accessors it lacks** — whether the cartridge declares a battery, and read/write access to its RAM. Accessors only: no behaviour change, and the core still knows nothing about files.
- [ ] **Step 2: Write the failing tests.** Round-trip: RAM written, saved, loaded into a fresh cartridge, identical. **The one that matters:** a save interrupted before the rename leaves the previous save intact and loadable. Simulate the interruption by writing the temporary file and not renaming it. Also assert a cartridge with no battery writes no file at all, and that a corrupt or truncated save is refused rather than loaded as garbage.
- [ ] **Step 3: Implement.** Write to a temporary file in the same directory, flush, then rename over the target — rename within a directory is atomic, a write in place is not. The save sits beside the ROM with a `.sav` extension.
- [ ] **Step 4: Wire it in.** Load on start if present, save on clean exit, and say so on stdout so the user knows a file was written.
- [ ] **Step 5: Verify and commit.**
